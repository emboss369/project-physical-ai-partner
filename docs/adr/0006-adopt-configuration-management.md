# ADR-0006: Adopt Configuration Management

- Status: Accepted
- Date: 2026-08-11

## Context

Project Physical AI Partner は複数の独立したマイクロサービスで構成される。サービスごとに環境変数や設定ファイルを独自に読み込むと、設定値の検証、型変換、エラー処理、機密情報の扱いが不統一になる。

各サービスが自身の設定を独立して所有しながら、共通した型安全な読み込みと検証の仕組みを利用できるConfiguration Managementが必要である。

## Decision

設定管理ライブラリとして **pydantic-settings** を採用する。

各サービスは `BaseSettings` を継承したサービス固有の設定モデルを定義する。設定モデルはサービスの起動時に生成・検証し、検証済みの設定をアプリケーションへ渡す。サービスの業務コードは `os.environ` を直接参照しない。

`shared` には設定読込を補助する共通基盤のみを置き、サービス固有の設定モデルやデフォルト値は置かない。

### Configuration Policy

- 本番環境の設定ソースは環境変数とする。
- `.env` はローカル開発でのみ利用し、Git管理しない。公開してよいキー名と例値だけを `.env.example` に記録できる。
- 設定モデルは型、必須値、制約、サービス固有の環境変数プレフィックスを宣言する。
- 設定値の優先順位は、明示的な初期化引数、環境変数、`.env`、secrets file、モデルのデフォルト値とする。
- 必須値の欠落や不正な値があれば、サービスは起動時に失敗する。
- ネストした設定の環境変数名は `__` を区切り文字として表現する。例: `LLM_MODEL__MAX_TOKENS`。
- APIキー、トークン、パスワードなどの秘密情報をログ、例外メッセージ、テスト出力へ出力してはならない。

## Alternatives Considered

### Python standard library (`os.environ`)

追加依存が不要で単純だが、型変換、バリデーション、`.env` の扱い、エラー形式を各サービスで実装する必要がある。複数サービスで設定規約を統一できないため採用しない。

### dynaconf

多層設定、複数ファイル形式、環境切替などを提供する。一方で、現在必要な環境変数中心の設定管理には機能が広く、サービスごとの設定所有を不明瞭にしやすい。複雑な多環境設定が必要になった時点で再評価する。

### environs

環境変数の型変換と`.env`の読み込みを簡潔に提供する。ただし、設定を宣言的なモデルとして表現し、サービス境界で一貫して検証するにはpydantic-settingsより手作業が増えるため採用しない。

### python-decouple

環境変数と設定ファイルの分離には適しているが、型付きの設定モデルと検証の標準化が不足するため採用しない。

### pydantic-settings (Adopted)

型ヒントによる設定モデル、環境変数・`.env`・secrets fileの読み込み、起動時バリデーションを提供する。サービス固有の設定を独立したモデルとして保持しながら、共通の開発規約を適用できるため採用する。

## Consequences

### Positive

- 設定の型変換とバリデーションを各サービスで統一できる。
- 不正な設定を起動時に検出でき、実行中の設定エラーを減らせる。
- 設定モデルがサービスの必要な外部依存を明示する。
- ローカル開発と本番環境で同じ設定インターフェースを利用できる。

### Negative

- pydantic-settingsとPydanticへの依存が追加される。
- 各サービスで設定モデルを定義・維持する必要がある。
- `.env` の誤った取り扱いによる秘密情報漏えいを防ぐため、開発者はポリシーを守る必要がある。
